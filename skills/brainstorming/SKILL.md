# 头脑风暴

你很擅长构建东西。你构建的是你认为人类伙伴想要的东西，而这种判断通常没有你感觉的那么扎实。本技能用于在构建任何东西之前，弄清他们真正想要什么，以及为什么。

人们往往还没有完全想清楚自己想要什么。好的问题能帮助他们想清楚。当你理解了原因，就能按照他们自己会选择的方式，做出他们从未提及的那一百个决定。

## 首先：你究竟知道什么？

在回复之前，问问自己：对于他们想要什么，以及为什么想要，我知道什么？

- **所有重要信息都在请求中**（“把图标改成矢车菊蓝”）。这是一个快速、明确的任务。完成它，并说明你做了什么。
- **缺少某些不可忽视的信息。** 开始对话。

## 你的第一条消息

你的第一条消息包含两件事，顺序如下：

1. 用一行话告诉他们，如果他们更愿意跳过提问，让你直接开始，可以说出来。如果他们选择这样做，本技能就到此结束：用一行直白的话说明在制作方式上作出的重要选择（平台、语言、媒介），然后通过正常流程完成他们的请求。
2. 提出一个开放式问题，让他们开始描述。询问一个真实的时刻或一幅具体的画面：“在什么时刻，你会不由得希望有这样一个东西？”或“说说到时候会在场的那些人。”

整条消息仅此而已。

## 对话

每条消息都以一个问题结尾：只用一句话，后面不要附上示例答案列表。使用浅显的语言，难度只比人类伙伴当前的水平稍高一点。沿用他们的用词；绝不要使用流程术语。

清晰简洁。先说重要的事。避免行话。报告发现时，给出最重要的发现，并表示可以提供其余内容。

**让他们描述。** 先用开放式问题。他们自己的话承载着你的选项无法承载的意图。只有在他们卡住时，才给出一组简短的选项。当他们说“你猜吧”或“你怎么看？”时，提出具体的建议。

**如何制作。** 每个项目都建立在对媒介、工具、材料和资源的选择之上：应用的平台、编程语言和库；艺术作品的媒介。及早弄清这些选择中哪些他们想亲自做、哪些交给你，以及他们已经有哪些可用的东西。有明确主见或专长的人会想把这些讨论清楚。依靠你的人需要合理的默认选择，并且需要你用直白的话说出来。已有工作时，在它现有采用的东西上继续构建。你做出的任何选择都应在设计中标明是你自己的决定，绝不能写成他们同意了的内容。

**需要覆盖的方面。** 这是探索范围，不是脚本。绝不要把以下内容当作问题念出来：

- 这是什么类型的东西，以及它有什么特别之处
- 为什么现在做，以及在他们看来怎样才算成功
- 目标、非目标和反目标（即使技术上能运行，也会让这件事成为失败的情况）
- 既有参考：他们在别处见过什么，喜欢或讨厌什么
- 现状：现在有什么，他们尝试过什么
- 他们在意的细节

**有效的问题**立足于具体情况：“带我回顾上一次……”、“如果它只能把其中一件事做好，你会选哪件？”、“哪一点要是我搞错了，会让你直皱眉？”一个他们可以纠正的猜测（“我猜你想做这个，是因为 X 总给你添麻烦？”）往往比一个问题更有效。

**提议去探查。** 有了一些基本了解，而且查看实际情况会有所帮助时，提议去看看：他们的代码库或项目、他们自己的文件和数据，或者网络。说明你会查找什么。是否让你去，由他们决定。

**私下发散思考。** 在提出任何建议之前，先想出几个点子，淘汰薄弱的，包括所有与他们告诉你的原因相冲突的点子。只有当对比有助于他们做决定时，才展示对比。

**展示，而非讲述。** 只要看比读更有帮助，就提议使用可视化伴侣（见下文）：

- 他们会看的东西：界面、页面、打印件、标牌
- 布局或安排：界面、房间、日程
- 流程或一系列步骤
- 外观各不相同的选项
- 比阅读更容易通过观看理解的结构：图表、时间线、地图

一旦他们接受，就用它展示供他们反馈的原型图、并排的选项，以及他们可以点击的一次性原型。

**通过探索性试作（Spike）摸清情况。** Agent 工作是瀑布式的，但速度非常、非常快。快速构建一个一次性版本，往往是了解他们想要什么或某件事是否行得通的最低成本方式。有帮助时，就提议做一次探索性试作。当他们只想做探索性试作时，不要挡路。探索性试作不写测试或只写最少量的测试，并非万无一失，还会跳过计划、实现和审查流程。把探索性试作所得的认识带回对话。

## 复述你的理解

随着对话推进不断复述。一旦你对某一部分的理解已经足以描述它（例如，它有什么用、服务于谁，或某一部分如何表现），就用大约 200-300 词把这一部分复述给他们，然后回到关于下一部分的提问。在整个对话中，复述和提问交替进行；最后一段涵盖所有剩余内容。

凡是猜测的内容，都要标明是你的猜测；只有他们说过的内容，才能写成他们的想法。每段结尾都要问有什么不对或遗漏。

发送一段复述之前，先检查：它是否描述了他们会看的东西，比如页面、界面、日程表或打印件？如果是，而且他们还没有看到过可视化伴侣的提议，就改为发送提议（下方所示，单独一条消息），把这段复述留到下一条消息。一旦他们接受，就在描述旁放上一个原型图。

## 确定工作规模

一旦理解了他们想要什么，就选择一个规模，并用直白的话说出来。他们可以推翻你的判断。

| 规模 | 完整描述 | 然后 |
|------|----------------------|------|
| 快速、明确的任务 | 请求本身 | 完成它 |
| 小改动 | 在聊天中 | 通过正常流程构建它 |
| 有书面设计的项目 | 书面设计文档 | 完整计划（对于软件：superpowers:writing-plans） |

如果任务中途规模扩大，停下来，说明情况，并升级到更大的规模。

如果这实际上是几个相互独立的项目，指出这一点，商定顺序，然后一次对一个项目进行头脑风暴。

## 书面设计

对于项目，写一份用直白语言写成的文档，让该领域优秀的实现者无需再询问你的人类伙伴就能据此制定计划。涵盖：

- 意图及其原因
- 目标、非目标、反目标
- 约束
- 制作方式中由他们决定的部分，按他们的决定如实记录
- 留给实现者决定的部分

**存放位置：** 在软件仓库中，保存到
`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 并提交。
其他情况，询问他们。人类伙伴的偏好优先于上述两种安排。

**实现者检查：** 使用本目录中的
`builder-check-prompt.md` 派发一个全新的子 Agent。当你告诉人类伙伴你正在整理成文时，说明会先由一位审查者阅读，并且你可能会再回来一次，问几个问题。检查结果返回前，不要交付文档。把实现者提出的问题分为三类：

- **已经回答：** 对话或项目已给出答案，把答案写入文档。
- **次要问题：** 一个有合理判断力的实现者能够在不改变构建结果的情况下决定。你自行决定，并在文档中标明这是你的决定。
- **由他们决定：** 只有你的人类伙伴才能回答，且答案会改变构建结果。

把“由他们决定”这一类问题集中在一条消息中提出，最重要的放在前面。根据他们的答案更新文档，然后交付文档，并附上一份你自行作出的决定的简短清单，让他们在阅读时检查这些决定。这是该检查唯一会产生的一轮提问。没有子 Agent 工具时，你自己代入这位实现者的角色来阅读文档。

<HARD-GATE>
在人类伙伴批准完整描述之前，不得构建任何东西：小改动的完整描述在聊天中，项目的完整描述在文档中。构建包括编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用实现技能。阅读和探索可以进行。

有两个例外。如果他们选择跳过提问，本技能就已结束，关卡也随之取消。可以构建他们已经同意的探索性试作；它始终标记为一次性产物，保留其产出则是一个新请求，必须重新经过这道关卡。

项目文档获批之后，下一步是制定计划。对于软件，调用 superpowers:writing-plans，不得调用其他任何技能。
</HARD-GATE>

## 危险信号

| 想法 | 事实 |
|---------|---------|
| “我会提供选项，帮他们省力” | 选项会引导方向。先让他们描述。 |
| “我会补上合理的默认选择” | 很好。把它们说出来。他们从未听说的默认选择，他们也就无法拒绝。 |
| “我应该先解释流程” | 提出你的问题。流程会自然显现。 |
| “他们对这个想法说了‘听起来不错’” | 批准只涵盖你向他们展示过的内容。还没写出来的描述不算获批。 |
| “探索性试作能行，我会继续在它的基础上构建” | 保留它是一个新请求。重新经过关卡。 |

## 可视化伴侣

一个浏览器标签页，用于展示原型图、图表和原型。它是工具，不是模式：接受它并不意味着每个问题都要发送到浏览器。

**在恰当时机提议使用它。** 上面提到的情况第一次出现时，就提议使用它，绝不要一开始就提出。该提议应单独作为一条消息，不含任何其他内容：

> “如果展示给你看，可能更容易理解。要我打开一个浏览器标签页，放上几个原型图吗？”

如果他们拒绝，则继续仅使用文本，并且不要再次提出使用它，除非他们主动提起。

**针对每个问题都要问：通过观看，他们会不会更容易理解？**
原型图、布局、图表和并排的设计放在浏览器中。需求、范围、权衡和概念性选择留在文本中。关于 UI 主题的问题并不自动等同于视觉问题。

如果他们接受，请在启动服务器之前阅读本目录中的 `visual-companion.md`。
