# 诊断 Superpowers

## 概述

与你的人类伙伴一起明确某次会话出了什么问题，读取
磁盘上的会话记录，并用证据报告发生了什么。你负责报告；
不要诊断 superpowers。对资料包或问题单进行分诊的人
决定是否改动 superpowers。

**核心原则：** 每项发现都必须引用 `path:line`。没有引用，就没有
发现。每个数字都来自会话记录或你运行的命令，
绝不能凭记忆提供。

## 工作流程

为每个步骤创建一个待办事项。第 5–7 步仅在各自声明的条件满足时执行。

1. **问题收集。** 每次只问一个问题，直到你能够写出一份
   陈述，明确会话（一个或多个）、轮次范围（若已知）、人类伙伴的
   预期、实际发生了什么，以及他们关心的可观测事项
   （实际耗时、token 数、重复动作、某个特定动作）。“耗时
   太久了”是抱怨，不是问题陈述。注明目标是否是
   superpowers 缺陷报告。
2. **定位。** 使用
   `references/session-discovery.md` 将每个会话定位到经过验证的绝对文件系统路径。通过引用
   首条提示和时间戳来确认过去的会话，并列出你排除的每个候选项及其
   原因，或填写“none”。列举子 Agent 的会话记录。创建
   `~/.superpowers/diagnosing-superpowers/<session-id>/`，将该
   路径告知人类伙伴，并在那里填写 `templates/case.md`，遵循其中
   关于环境和技能观察记录的来源追溯规则。
3. **分诊。** 亲自读取所报告问题附近的记录片段。然后
   按维度并行派发分析员子 Agent，每个维度一个，为每个子 Agent 提供
   案例文件路径、`prompts/analyst-common.md`，以及 `prompts/` 中的一个维度文件：
   `skill-timeline.md`、
   `plan-adherence.md`、`repeated-work.md`、`stumbles.md`、
   `quality-evidence.md`、`request-conflicts.md`、`cost-and-time.md`。
   当会话记录较长时，按轮次范围拆分维度。丢弃
   任何没有 `path:line` 引用的返回发现。
4. **报告。** 按顺序填写 `templates/report.md` 的每个章节，将
   报告写入工作区，展示报告，并提供路径。核查所引用的内容
   实际上能证明什么，并保留支撑报告的案例资料；符号链接别名不属于
   冗余副本。
5. **GitHub 问题单**——当报告 §7 判定为 possible 或 likely，或你的人类伙伴
   提出要求时执行。根据
   `references/github-issues.md` 按症状搜索未关闭和已关闭的问题单。展示匹配结果，并建议将
   报告添加到最接近的问题单中。若无匹配，则填写 `templates/issue.md`，将其写入
   工作区，展示确切文本，并且仅在
   获批后创建问题单。`gh` 无法附加文件；如果已有资料包，则将
   其路径提供给人类伙伴，让他们在浏览器中添加为附件。
6. **导出**——仅在人类伙伴要求资料包时执行；绝不能
   擅自构建。如果问题收集阶段的目标是缺陷报告，就只说明一次可以按需提供
   经脱敏的资料包，然后等待。询问脱敏
   级别，并说明各级别包含哪些内容：skeleton（不含工具结果正文）、
   evidence（仅为被引用的事件保留正文）、full。按
   `templates/bundle-README.md` 构建资料包，派发 `prompts/scrub.md`，接着
   派发 `prompts/scrub-audit.md`，反复执行这两者，直到审计返回 CLEAN。
   在展示最终脱敏日志、文件列表以及隐私与证据方面的结果之前，
   完成资料包模板中的证据检查和核对。
   仅在获批后才进行归档（`zip -r` 或 `tar -czf`）。提供归档文件
   路径时，说明其中包含什么，指引他们到脱敏日志中查看替换记录，并
   说明脱敏可能会有遗漏：他们必须在分享前逐一检查所有文件。
7. **类似会话**——在被要求时执行。将已确认的发现转化为
   特征签名，按 mtime 和大小列出候选项，找出标记行号，
   为每个候选项并行派发 `prompts/similar-session.md`，并
   追加报告 §9。

## 快速参考

全部七名分析员始终都要运行。这张表说明你在第 3 步应亲自读取
哪一部分，以及在判定中应优先呈现哪些发现。

| 抱怨 | 优先读取、优先呈现 |
|---|---|
| “耗时太久了” | cost-and-time, stumbles |
| “它为什么做了这些额外工作？” | repeated-work, plan-adherence |
| “为什么这么贵？” | cost-and-time |
| “它究竟在搞什么鬼？”（仍在运行） | skill-timeline；在覆盖情况中注明 in-progress |
| “它无视了计划” | plan-adherence，先查看上下文压缩相关行 |
| “技能 X 从未触发” | skill-timeline |

## 硬性规则

- **上下文安全。** 一行会话记录就可能有一兆字节。对于
  每个会话文件，每次都要遵循 `references/context-safety.md`。
- **只读。** 绝不修改、移动或删除会话文件。
- **向子 Agent 提供精确路径。** 子 Agent 的“当前会话”是它
  自己的会话。传入绝对路径和 id。
- **仅限人类提示。** Hook 输出、系统提醒和工具结果
  都不是人类伙伴的话语。在子 Agent 的会话记录中，“user”指的是
  父 Agent。
- **不得诊断 superpowers。** 报告 §7 说明涉及情况，然后到此为止。
  绝不指认技能中的缺陷，也不提出改动。人类伙伴
  坚持要求修复，也不能豁免这条规则；指明问题单步骤，并
  说明可按需提供资料包。也不要向
  人类伙伴提供建议。
- **审批关卡。** 在人类伙伴看过脱敏
  日志和文件列表之前，不得归档。在他们批准确切
  文本之前，不得创建问题单或发布评论。
- **先收集问题，再分析。** 人类伙伴回答之前，第 2–7 步中的任何工作
  都不得开始。如果他们不在，就写下问题并停止。
  你替他们重构出的陈述不算回答。一项
  已经界定范围的请求——一个具体事件、当前正在运行的内容，或
  要执行的分析——本身就是陈述：先回答该请求，再提问。
  针对整个会话的“为什么”是抱怨。

## 警示信号

| 想法 | 实际情况 |
|---------|---------|
| “问题很明显，跳过问题收集” | 问题陈述界定所有工作的范围。提问。 |
| “他们不在，所以我来重构陈述” | 你无法重构他们想要什么。写下问题并停止。 |
| “我现在先全面扫描，最后再问” | 未界定范围的全面扫描会把他们的预算花在错误的问题上。先提问。 |
| “他们想要缺陷报告，所以我现在就构建资料包” | 资料包就是他们打包后的会话数据。只有他们提出要求时才构建。 |
| “只是小范围、有针对性的编辑，无需调整结构” | 无论改动多小，都不由你决定。报告证据；由分诊者决定。 |
| “每个 token 的价格众所周知” | 未由你从会话记录计算得到的数字就是编造的。给出引用，否则舍弃。 |
