# 编写计划

## 概述

为一名尚未看过此代码库或此规格说明的工程师编写实施计划。假设他们一旦知道确切的接口和确切的测试，就会使用项目所用语言编写符合惯用风格的代码，并会在计划留有选择余地的每一处做出合理选择。他们无法知道的是你已经做出的决定：哪些文件、哪些名称和签名、规格说明中的哪些值、哪些测试能验证每项任务。记录这些决定。将完整计划拆成小块任务交给他们。DRY。YAGNI。TDD。频繁提交。

**开始时宣布：**“我正在使用 writing-plans 技能来创建实施计划。”

**上下文：**如果在隔离的工作树中工作，它应当已在执行时通过 `superpowers:using-git-worktrees` 技能创建。

**将计划保存至：**`docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- （用户对计划位置的偏好会覆盖此默认值）

## 范围检查

如果规格说明涵盖多个相互独立的子系统，则在头脑风暴期间就应该已将其拆分为多个子项目规格说明。如果尚未拆分，建议将其拆成单独的计划——每个子系统一份。每份计划都应独立产出可运行、可测试的软件。

## 文件结构

在定义任务之前，梳理将创建或修改哪些文件，以及每个文件负责什么。分解决策将在这里确定下来。

- 设计边界清晰且接口定义明确的单元。每个文件都应只有一项明确的职责。
- 对于能够一次纳入上下文的代码，你的推理效果最佳；当文件职责聚焦时，你的编辑也更可靠。相比庞大且承担过多职责的文件，应优先选择更小、更聚焦的文件。
- 会一起变更的文件应该放在一起。按职责拆分，而不是按技术层拆分。
- 在现有代码库中，遵循既有模式。如果代码库使用大文件，不要单方面重构——但如果你正在修改的文件已经变得难以驾驭，那么在计划中加入拆分是合理的。

此结构会为任务分解提供依据。每项任务都应产出自包含的变更，且这些变更本身应独立合理。

## 任务大小适配

任务是具备自身完整测试周期、且值得由一位新的审查者设置一道关卡的最小单元。划分任务边界时：将设置、配置、脚手架和文档步骤并入其可交付成果需要这些步骤的任务中；仅当审查者能够有意义地拒绝一个任务、同时批准其相邻任务时才进行拆分。每项任务都以可独立测试的可交付成果结束。

## 步骤粒度

**每个步骤都是一个具有可检查结果的操作：**
- “编写失败的测试”——一个步骤
- “运行它以确保它失败”——一个步骤
- “实现让测试通过所需的最少代码”——一个步骤
- “运行测试并确保它们通过”——一个步骤
- “提交”——一个步骤

## 计划文档标题

**每个计划都必须以此标题开头：**

```markdown
# [功能名称] 实施计划

> **面向 Agent 型工作者：** 必需的子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 来逐项任务实施此计划。步骤使用复选框（`- [ ]`）语法进行跟踪。

**目标：** [用一句话描述要构建的内容]

**架构：** [用 2-3 句话说明实现方法]

**技术栈：** [关键技术/库]

**规格说明：** [本计划实现的规格/设计文档路径——计划以规格说明为依据，规格说明会随计划一起传递；执行者需要同时阅读二者]

## 全局约束

[规范中的项目级要求——最低版本、依赖限制、
命名和文案规则、平台要求——每项一行，精确值逐字
从规范中复制。每项任务的要求均隐含包含本节。]

<a id="review-focus"></a>
## 审查重点

[规格说明所隐含、但没有任何任务的测试覆盖，且最可能给此软件的
使用者带来问题的五类输入或故障模式——每项一行，写明输入或条件
以及人们合理预期的行为，最可能带来问题的排在最前。规格说明是愿景
文档：它说明软件必须做什么，而不是软件将遇到的一切；它对某种
输入保持沉默，并不意味着允许这种输入破坏程序。在此处对照
规格说明，一次性写下这份列表。然后，对每一行，将锁定相应行为的
测试添加到负责相应代码的任务中，采用该任务自己的步骤风格。]

---
```

## 任务结构

````markdown
### Task N: [组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 使用：[此任务使用前序任务的哪些内容——写出精确签名]
- 产出：[后续任务依赖的内容——写出精确的函数名、参数和返回类型。
  任务实现者只能看到自己的任务；他们通过此块了解相邻任务使用的名称和类型。]

- [ ] **步骤 1：编写会失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试以验证其失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL，并显示“函数未定义”

- [ ] **步骤 3：在 `exact/path/to/file.py` 中实现 `function(input: InputType) -> ResultType`**

当签名和测试仍留有选择余地时，用一行说明实现方法
（使用哪个库调用、哪种数据结构）；仅对签名和测试无法
确定的算法提供代码块。

- [ ] **步骤 4：运行测试以验证其通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 步骤包含的内容

当实现者能够根据一个步骤写出恰好一项合理的内容时，该步骤就算写完了。这就是全部要求：明确无歧义，而非面面俱到。每类步骤只包含使其明确无歧义所需的内容，不包含其他内容：

- **测试步骤：** 以代码形式给出测试名称及其断言，其中使用规格说明中的精确值。
- **代码步骤：** 精确的签名（名称、参数、返回类型）、所在文件，以及规格说明明确规定的具体值。函数体由实现者编写。只有当算法无法由签名和测试确定，或规格说明固定了精确文案时，才提供函数体。
- **验证步骤：** 要运行的命令，以及表示通过的输出。
- **对另一项任务的引用：** 该任务的接口块说明了要使用的内容；计划不重复该任务的代码。

计划是实现者无法独自做出的决定的集合。如果一份计划比它描述的代码还长，那它已经是在直接写代码了。那些没有做出任何决定的行（“TBD”、“处理边界情况”、“添加适当的验证”、“为上述内容编写测试”、没有任何任务定义的类型或函数）则是相反的失败情况，自我审查会发现这两类问题。

## 自我审查

撰写完整计划后，以全新的视角审视规范，并对照规范检查计划。这是你自己执行的检查清单——不是派遣子 Agent。

**1. 规范覆盖：**快速浏览规范中的每个章节/要求。你能指出实现它的任务吗？列出所有缺漏。

**2. 步骤扫描：**每个步骤都必须让实现者能够写出恰好一项合理的内容，并且不得包含更多内容：没有做出任何决定的行是缺漏，而签名和测试已经确定的函数体则是程序实录。两者都要修复。

**3. 类型一致性：**你在后续任务中使用的类型、方法签名和属性名称，是否与早期任务中的定义一致？任务 3 中名为 `clearLayers()` 的函数到了任务 7 却变成 `clearFullLayers()`，这就是一个错误。

**4. 审查重点：**对于规格说明所隐含的每类输入或故障模式，是否有任务的测试覆盖它？将未覆盖且最可能给人带来问题的五项放入“审查重点”一节，并为该节中的每一行在负责相应代码的任务中添加测试。该节为空意味着你已经检查过并且没有发现这样的情况，而不是跳过了检查。

**5. 篇幅比例：**对比计划与规格说明的长度。如果计划的长度是它所实现的规格说明的数倍，那它就是程序的实录，而非计划。如果代码块占据了文档的大部分内容，就用签名、测试名称和断言替换函数体，并检查每个步骤是否仍然明确无歧义。

如果发现问题，就地修复。无需重新审查——只需修复并继续。如果发现某项规范要求没有对应任务，就添加该任务。

## 执行交接

保存计划并完成自我审查后，提供链接供你的人类伙伴阅读。如果他们已经明确指定了执行方式，请让他们审阅计划并确认计划涵盖了他们想要的内容；在实施前等待他们完成审阅，然后使用已保留的方式。否则，请让他们在实施前审阅计划并选择执行方式。

**当尚未指定执行方式时：**

**"计划已完成并保存到 `docs/superpowers/plans/<filename>.md`。请审阅计划。你更倾向于哪种执行方式？**

- **子 Agent 驱动** - 每项任务由一个全新的子 Agent 实施，并由一位全新的审查者检查后，才开始下一项任务，最后对整个分支进行审查。最为彻底；代价是每项任务和每次审查都需要一个全新的上下文。
- **原生执行** - 我在本会话中按照此运行框架的工作执行方式，亲自实施每项任务，然后由一位使用能力最强模型的全新审查者检查整个分支。成本最低、速度最快；直到最后才进行独立审查。使用中档会话模型也能很好地运行，因为计划承载了设计。

**对于这份计划，我推荐 <两者之一>，因为 <来自计划的一句话：各项任务在多大程度上依赖彼此的接口、有多少项任务、错误随软件交付会造成多大代价>。计划是否涵盖了你想要的内容，我们应该使用哪种方式？"**

**当已经指定执行方式时：**

**"计划已完成并保存到 `docs/superpowers/plans/<filename>.md`。请审阅计划。它是否涵盖了你想要的内容？"**

**如果选择子 Agent 驱动：**
- **必需的子技能：**使用 superpowers:subagent-driven-development

**如果选择原生执行：**
- **必需的子技能：**使用 superpowers:executing-plans
